# SAT Sharks 2.0 — Phase 1: Project Foundation & Architecture

You are working on the SAT Sharks 2.0 project.

The client wants a SAT practice platform based on the provided project proposal and a reference website/interface. We will build the project in multiple phases.

## IMPORTANT

This is **PHASE 1 ONLY**.

Do NOT attempt to build the complete website.
Do NOT implement the SAT test engine yet.
Do NOT implement analytics, leaderboard, payments, subscriptions, or advanced admin features yet.
Do NOT create fake functionality just to make the project look complete.

Your job in this phase is to establish a clean, production-ready foundation that later phases can build on.

Before writing code:

1. Read the project proposal located at:
   `/docs/SAT_Sharks_Proposal.pdf`

2. Read any existing project documentation.

3. Inspect the current repository structure.

4. If a reference folder exists, inspect:

   * `/reference/screenshots`
   * `/reference/network`
   * `/reference/notes.md`

5. If the repository is empty, create the project structure described below.

---

# 1. Technology Stack

Use the following architecture unless the existing repository already contains a strong reason to change it:

### Frontend

* Next.js
* TypeScript
* Tailwind CSS
* React
* TanStack Query where client-side server-state management is required

### Backend

* Node.js
* Express
* TypeScript

### Database

* MongoDB
* Mongoose

### Background processing

Prepare the architecture for:

* Redis
* BullMQ
* Worker process

The worker will later handle:

* paper importing
* scraping/API ingestion
* PDF processing
* AI extraction
* image processing
* analytics jobs

Do NOT implement the complete worker functionality in Phase 1.

### Deployment target

* Frontend: Vercel
* Backend: Railway initially
* MongoDB: MongoDB Atlas
* Object/file storage: S3-compatible storage

Keep the architecture portable so the backend/worker can later move to AWS if required.

# 6. Initial Database Models

Based on the proposal, design the database foundation.

Do NOT implement every future model yet.

* password hash

### Paper

* description
* source
* status
* section information
* metadata
* createdAt
* updatedAt

Paper status should support the proposal's workflow:

* Draft
* Published
* Hidden

### Question

Prepare the foundation for:

* paperId
* section
* module
* questionNumber
* questionType
* prompt/content
* choices
* correctAnswer
* explanation
* difficulty
* topic
* skill
* assets
* metadata
* status

Use references between Paper and Question.

Create appropriate indexes for fields that will later be queried frequently.

Do not over-engineer the schema before the actual question structure is finalized.

# 9. Paper Import Architecture

This project will eventually need to obtain SAT questions/papers and convert them into our own normalized database structure.

Design the architecture now, but do not implement the entire scraper/import system.

Create:

`docs/scraping.md`

Document this pipeline:

Source
↓
Fetcher
↓
Raw data
↓
Normalizer
↓
Question/Paper schema
↓
Draft
↓
Admin Review
↓
Approved
↓
Published

The system should be designed so that if a structured API/network response is available, we can use it instead of relying on fragile DOM scraping.

PDF/AI extraction should remain a fallback pipeline.

Do not hardcode a scraper for the reference website in Phase 1.
